# 테스트 코드 동기화

소스 파일의 비즈니스 로직 변경에 맞춰 대응하는 테스트 파일을 생성하거나 업데이트합니다.

## 사용법
```
/sync-test [파일경로]
```

예시:
- `/sync-test hooks/useBookmark.ts`       ← 로직 변경 후 테스트 업데이트
- `/sync-test store/exploreStore.ts`      ← 새 액션 추가 후 테스트 추가
- `/sync-test lib/utils/math.ts`          ← 새 유틸 함수 테스트 생성

## /generate-test 와의 차이

| | `/generate-test` | `/sync-test` |
|---|---|---|
| 용도 | 테스트 없는 파일에 최초 생성 | 기존 테스트를 소스 변경에 맞게 동기화 |
| 기존 테스트 | 덮어쓰지 않음 | 변경된 부분만 정밀 업데이트 |
| git diff 활용 | X | O (무엇이 바뀌었는지 파악) |

## 지시사항

**대상:** $ARGUMENTS

### 1단계: 변경 내용 파악

다음을 순서대로 실행하세요:

```bash
# 소스 파일에서 무엇이 바뀌었는지 확인 (아래 순서로 시도)
git diff -- [파일경로]           # unstaged 변경사항
git diff --staged -- [파일경로]  # staged 변경사항
git diff HEAD -- [파일경로]      # 마지막 커밋 기준 (staged+unstaged 합산)
git diff HEAD~1 -- [파일경로]    # 위 명령으로 diff가 없으면 시도 (이미 커밋된 경우)
```

git diff 결과를 분석해 다음을 식별하세요:
- **추가된 함수/로직** → 새 테스트 케이스 추가 필요
- **수정된 함수 시그니처** → 기존 테스트의 mock/인자 업데이트 필요
- **삭제된 함수** → 해당 테스트 케이스 제거 필요
- **변경된 에러 처리/분기** → 에러 케이스 테스트 업데이트 필요

git diff가 없으면(새 파일이거나 이미 커밋됨) 소스 파일 전체를 읽고 현재 테스트와 비교하세요.

### 2단계: 소스 파일과 테스트 파일 비교

두 파일을 읽어서 **갭 분석**을 수행하세요:

```
소스에 있지만 테스트에 없는 것 → 추가
소스에서 변경됐지만 테스트가 구 버전인 것 → 업데이트
테스트에 있지만 소스에서 삭제된 것 → 제거
```

### 3단계: 최소 변경 원칙으로 업데이트

**반드시 지킬 규칙:**
- **이미 통과하는 테스트는 건드리지 않는다** — 변경이 필요한 케이스만 수정
- **테스트 파일 전체를 다시 쓰지 않는다** — 필요한 부분만 Edit
- 새 테스트는 기존 describe 블록 안에 추가 (새 블록 생성 최소화)
- mock 업데이트 시 다른 테스트에 영향 없는지 확인

### 4단계: 테스트 실행으로 검증

```bash
pnpm test -- [테스트파일경로] --no-coverage
```

실패하면 반드시 수정 후 재실행. 모든 테스트가 통과해야 완료.

### 5단계: 결과 보고

완료 후 다음 형식으로 보고하세요:
```
✅ 동기화 완료: [테스트파일경로]

추가된 테스트:
- [describe] > [it 설명]

업데이트된 테스트:
- [describe] > [it 설명]: [변경 이유]

제거된 테스트:
- [describe] > [it 설명]: [소스에서 삭제됨]

테스트 결과: X passed, 0 failed
```

## 주의사항

- **타입 에러**가 발생하면 소스 파일의 새 타입을 확인하고 mock 데이터를 맞춰 수정
- **jest.mock 경로**가 바뀌었다면 import 경로 변경도 함께 반영
- `__tests__/utils/factory.ts`에 새 mock 생성자가 필요하면 추가
